## Landmines (found by the completeness critic, outside the fork diff)

### L1. OTA 'Check for Updates' will replace the fork with upstream CrossInk — wiping all 7 fork features and invalidating every book cache (no lens covered the OTA updater)

Verified end-to-end. /Users/alasdairthong/CrossInked/src/network/OtaUpdater.cpp:25-26 defaults to upstream: `#define CROSSINK_OTA_RELEASE_URL "https://api.github.com/repos/uxjulia/CrossInk/releases/latest"` and grep confirms NO override of CROSSINK_OTA_RELEASE_URL anywhere in platformio.ini or elsewhere. The fork keeps upstream's version namespace — platformio.ini:7 `crossink_version = 1.3.4` — and isUpdateNewer() (OtaUpdater.cpp:396-406) does a plain `compareVersions(latestVersion, CROSSINK_VERSION) > 0`. So the moment upstream publishes 1.3.5, Settings > Check for Updates (SettingsActivity.cpp:730 -> OtaUpdateActivity) offers an 'update' that flashes upstream firmware via ota_boot::switchTo, with no hint it removes CrossInked. Consequences: (a) all fork features silently vanish — and per the user's setup the fork exists only locally (release.yml is still upstream's, `git config user.name "uxjulia"` at .github/workflows/release.yml:97; no fork release channel exists), so there is no reinstall path without a local rebuild; (b) upstream still uses BOOK_CACHE_VERSION 8 while the fork bumped to 9 (lib/Epub/Epub/BookMetadataCache.cpp:15) and load rejects any mismatch (line 421 `if (version != BOOK_CACHE_VERSION)`), so every one of the 1,852 books re-parses its full OPF/spine on next open; (c) all content.key sidecars become unmaintained junk that goes stale under upstream (books moved there keep old source paths), poisoning fork cache-adoption if the fork is ever reflashed. Separate forward hazard from the same file: the fork consumed upstream's NEXT sequential cache version (9). When upstream itself bumps 8->9 for a different format change, magic+version will match but payload semantics differ in both directions — fork-written book.bin accepted and misread by upstream and vice versa, with no divergence detection. Fixes are cheap: define CROSSINK_OTA_RELEASE_URL to a fork release source or gate the menu item behind an explicit 'this installs upstream CrossInk and removes CrossInked features' confirmation, and move BOOK_CACHE_VERSION into a disjoint range (e.g. 0x80|N) or change BOOK_CACHE_MAGIC for the fork.

### L2. The 'progressive-JPEG crash' KNOWN LEAD is already fixed in this tree — and half of the audit's proposed JPEGDEC improvement is redundant

Two consequences for the audit: (1) its proposed improvement 'Apply the JPEGDEC progressive patches to the simulator build + fail loudly on unpatchable libdep' is half-done already — patch_jpegdec.py ALREADY fails loudly (`raise SystemExit(1)` when a patch does not apply cleanly, `RuntimeError` when the patch dir is missing/empty); only the simulator-env half is real work (the env:simulator extra_scripts block at platformio.ini:190-195 omits patch_jpegdec.py while pulling the same unpatched JPEGDEC pin at line 200 with CROSSPOINT_SIM_USE_NATIVE_DECODERS, so the sim exercises the buggy decoder the device never runs). ### HIGH

#### F1. Cache adoption (#5) silently fails on device whenever the destination cache dir already exists — prewarm and several action flows pre-create it, guaranteeing failure

`lib/Epub/Epub.cpp:579-630` — verifier votes 3/3

tryAdoptOrphanCacheByContentKey() finishes with 'Storage.rename(adoptFrom.c_str(), cachePath.c_str())', but by the time Epub::load() runs, cachePath already exists as a (freshly created, empty) directory in several flows: PrewarmCoversActivity.cpp:34-36 calls 'epub.setupCacheDir();' immediately before 'epub.load(true, true)' — the exact maintenance pass a user runs after bulk-renaming books; EpubReaderActivity::onEnter/drawCurrentPageToBuffer (EpubReaderActivity.cpp:1651, 4503) and loadBookRenderMode/saveBookRenderMode (1077-1090) call setupCacheDir() before load; BookActions::toggleEpubCompleted (BookActions.cpp:135) does the same from the browser long-press menu; and Clear Reading Cache recreates every epub_* dir to restore preserved stats*.bin (BookCacheUtils.cpp restorePreservedFiles). The guard at Epub.cpp:580 only checks book.bin ('BookMetadataCache::exists' = 'Storage.exists((cachePath + bookBinFile))', BookMetadataCache.cpp:390-392), so the empty dir slips through. On device, Storage.rename goes through SdFat's FAT rename, which fails when the destination path exists (it creates the new directory entry with O_CREAT|O_EXCL semantics); the return value is ignored, so adoption silently no-ops, a fresh cache is built, book.bin then exists forever so adoption is never re-attempted — reading progress (progress.bin), stats and reader settings in the orphan cache are permanently stranded, and the orphan dir leaks (reaper #8 unimplemented). The simulator masked this: its HalStorage::rename is POSIX '::rename(o.c_str(), n.c_str())' (.pio/libdeps/simulator/simulator/src/HalStorage.cpp:343-351), and POSIX rename succeeds when the destination is an existing EMPTY directory — so simulator testing shows the feature working while the device build cannot; the sim-verified log line in CROSSINKED.md proves nothing about hardware. Upstream itself knows the SdFat constraint: migrateLegacyCachePath bails with 'if (Storage.exists(cachePath.c_str())) return;' before its own rename (Epub.cpp:177-180). The setupCacheDir() pre-calls are also redundant — load() calls setupCacheDir() itself on the build path (Epub.cpp:710), AFTER the adoption attempt.

**Fix:** (1) Delete the redundant epub.setupCacheDir() call in PrewarmCoversActivity::stepWork (load() creates the dir itself when building), and audit the other pre-load setupCacheDir() call sites. (2) Harden tryAdoptOrphanCacheByContentKey: if Storage.exists(cachePath) && !BookMetadataCache::exists(cachePath), remove the empty pre-created dir (Storage.rmdir — succeeds only when empty; if non-empty, merge/preserve stats*.bin files into the adopted dir) before the rename. (3) Check the rename return value and LOG_ERR on failure instead of the silent comment. Then verify adoption end-to-end: rename an epub, run prewarm, confirm progress survives — ideally also make the simulator's rename fail on existing destinations to keep sim/device semantics aligned.

#### F2. Adoption scan is O(N) SD path-lookups (plus duplicate full OPF parse) per cache miss — O(N²) prewarm and minutes-long stalls opening any new book at ~1,850 cache dirs

`lib/Epub/Epub.cpp:579-630` — verifier votes 3/3

On EVERY Epub::load(buildIfMissing=true) where book.bin is missing, tryAdoptOrphanCacheByContentKey() (a) does a full container.xml + content.opf expat parse ('parseContentOpf(meta, false)', line 584) that the real cache build immediately repeats at line 727 — doubling OPF-parse cost on every first open; and (b) iterates every '/.crosspoint/epub_*' entry, calling Storage.exists(<dir>/content.key) AND Storage.readFile(<dir>/content.key) per candidate (lines 602-611), with no cap, no early bail-out, running synchronously with the UI blocked. Each exists()/readFile() is a full absolute-path lookup, which on FAT linearly scans the /.crosspoint directory: with the user's 1,852 books fully prewarmed, /.crosspoint holds ~1,852 subdirs whose 'epub_%016llx' LFN names occupy ~3 dir slots each (~178 KB directory), so an average lookup reads ~89 KB over SPI. Two lookups x 1,852 candidates is on the order of 300+ MB of SD directory reads — tens of seconds to minutes of frozen UI added to the first open of ONE newly added book, on battery. During a fresh prewarm the cost compounds quadratically (book k scans the k-1 caches created before it; ~1.7M sidecar opens across the run), plausibly adding an hour or more of pure adoption-scan SD churn that dominates the walk's runtime. The scan also re-runs for every book reopened after 'Clear Reading Cache' (dirs survive holding stats*.bin, book.bin gone), and it runs even when zero renames happened — it cannot distinguish 'new book' from 'renamed book' without reading every sidecar.

**Fix:** Replace per-dir content.key sidecar reads with a single flat registry (e.g. /.crosspoint/content_keys.idx, one 'key<sep>cacheDirName<sep>sourcePath' line appended/updated by writeContentKeySidecar) so a miss costs one small sequential file read, verifying the winning candidate's real content.key before renaming; fall back to the directory walk only if the index is missing. Also: pass an allowAdoption=false flag from PrewarmCoversActivity (misses are expected there and adoption of never-cached books is pointless); scan the directory handle first and only run parseContentOpf if a candidate exists (or reuse the parsed metadata in the build path so the OPF isn't parsed twice); read candidate files relative to the already-open directory iterator (SdFat FsFile::open(&dir, name, O_RDONLY)) to avoid per-candidate O(dir-size) path resolution; drop the redundant Storage.exists() (readFile already fails cleanly); and cap the scan so worst-case open latency stays bounded.

#### F3. Prewarm run is silently killed by the auto-sleep timer — no preventAutoSleep() override

`src/activities/settings/PrewarmCoversActivity.h:13-37` — verifier votes 3/3

PrewarmCoversActivity overrides skipLoopDelay() but NOT preventAutoSleep() (base Activity.h:49 returns false). The main loop only resets the inactivity timer on button/tilt activity or activityManager.preventAutoSleep() (src/main.cpp:1004-1010), and calls enterDeepSleep(true) after SETTINGS.getSleepTimeoutMs() (src/main.cpp:1046-1049; default sleep timeout is minutes — SLEEP_5_MIN per CrossPointSettings.cpp:604 / sleepTimeoutMinutes=10 per CrossPointSettings.h:375). During WORKING no buttons are pressed, so a 30-90 minute walk of 1,852 books is unconditionally deep-slept minutes in — enterDeepSleep(true) replaces the activity, all walk state (dirStack/pendingFiles/counters) is lost, and the user finds the device asleep with the job partially done and no indication why. Every other long-running activity overrides this (OtaUpdateActivity.h:36, SdFirmwareUpdateActivity.h:37, FontDownloadActivity.h:39, KOReaderSyncActivity.h:43, KOReaderAuthActivity.h:20), so the fork missed the established pattern. The simulator masks it (enterDeepSleep is a no-op there). Secondary: skipLoopDelay() returning true unconditionally busy-spins the loop with yield() at forced-full CPU (main.cpp:1088-1090) while sitting idle on the WARNING and DONE screens.

**Fix:** Add state-scoped overrides mirroring OtaUpdateActivity: `bool preventAutoSleep() override { return state == WORKING; }` and change skipLoopDelay() to `return state == WORKING;`. Scoping to WORKING is important: an unconditional `return true` would leave the device spinning at full clock, never sleeping, on the DONE screen after an unattended run — draining the battery to zero.

#### F4. Prewarm generates cover/thumbnail artifacts at sizes no UI surface ever requests — the stutter it exists to fix is not fixed

`src/activities/settings/PrewarmCoversActivity.cpp:37-38` — verifier votes 3/3

stepWork() calls 'epub.generateThumbBmp(0, 0)', which normalizeThumbDimensions (Epub.cpp:45-52, kDefaultThumbHeight=180, width=(180*3+2)/5=108) turns into thumb_108x180.bmp. Thumbnail caches are dimension-keyed — getThumbBmpPathForDimensions embeds WxH in the filename and cachedBmpMatchesDimensions requires an exact (or contained-adaptive) match — and no consumer requests that size: the recent-books grid uses 123x180 (RecentBooksGridActivity.h:13-14 'COVER_HEIGHT = 180; COVER_WIDTH = 123', generated on demand at RecentBooksGridActivity.cpp:288 behind a blocking 'Loading' popup), the default/base themes request heights 370/260/600 (BaseTheme.h:144, RoundedRaffTheme.h:27), the Lyra carousel uses 296x468/540 and 200x390 (LyraCarouselTheme.h:42-45, HomeActivity.cpp:611-616), the Minimal home uses an ADAPTIVE thumb (different filename AND generation variant, generateAdaptiveThumbBmp with height 525, HomeActivity.cpp:314-317, 674-676), and the sleep cover uses generateCoverBmp(cropped) where cropped depends on SETTINGS.sleepScreenCoverMode (SleepCoverAssets.cpp:39-43) while prewarm only generates the uncropped cover.bmp. So after a 30-90 minute battery-draining walk of 1,852 books, every screen still JPEG-decodes covers on first visit — the activity's own header ('so first browse of the recent grid / carousel isn't stuttery', PrewarmCoversActivity.h:8-10) is not met. Meanwhile ~1,850 never-read ~5KB BMPs (~9-18MB) are written to SD, every cover is JPEG-decoded twice (cover + useless thumb) roughly doubling runtime/battery cost, and the expensive full-screen cover.bmp pass (decode + Atkinson dithering, ~2-6 s/book) only serves sleep-screen covers. Only the book.bin metadata prewarm delivers lasting value.

**Fix:** Generate the exact artifacts the UI consumes — mirror HomeActivity::loadRecentCovers and SleepCoverAssets::prepareEpub: generateThumbBmp(RecentBooksGridActivity::COVER_WIDTH, COVER_HEIGHT) for the grid; the active theme's home-cover size (metrics.homeCoverHeight, Lyra kCenterThumbW/H + kSideCoverW/H, or generateAdaptiveThumbBmp(MinimalMetrics::homeCoverImageWidth, homeCoverImageHeight) for Minimal); and generateCoverBmp(cropped) matching SETTINGS.sleepScreenCoverMode. Drop the useless (0,0) call, and consider making the expensive full-screen cover pass optional to roughly halve the run time.


### MEDIUM

#### F5. Cache adoption validates nothing but the title|author hash — adopts a different edition's cache and serves stale spine/layout/progress without re-validation

`lib/Epub/Epub.cpp:570-630` — verifier votes 3/3

The adoption key is fnvHash64(title + 0x1f + author) with no content identity, and the only safety check is that the sidecar's recorded source path no longer exists. When a book is replaced by a different edition (old file deleted, new file at a new path, same OPF title/author — a normal Calibre re-export/re-encode workflow for this user), adoption renames the old edition's entire cache dir into place and NOTHING revalidates it afterwards: BookMetadataCache::load() checks only magic, version, and string structure (lines 394-455) — no source-file size/CRC/mtime check anywhere. The adopted book.bin carries the OTHER file's spine hrefs and cumulative sizes, sections/ carries the other edition's pre-rendered layout, and progress.bin carries a spineIndex/page into the other edition. On device: reader resumes at a wrong or nonexistent spine position, chapter opens fail when a cached spine href doesn't exist in the new zip (readItemContentsToStream returns false), progress percentages are computed from the wrong cumulative sizes, TOC entries point at missing hrefs, and the stale cover.bmp/thumbnails keep being served (generateCoverBmp returns early because cover.bmp exists).

**Fix:** Fold a content fingerprint into the key or sidecar: hash the raw content.opf bytes (the adoption path already streams content.opf through parseContentOpf) or use the OPF dc:identifier, and/or record the source EPUB's file size as a third content.key line — only adopt when the fingerprint/size matches the current file. Renames keep the fingerprint stable; edition swaps change it and correctly fall through to a fresh build.

#### F6. Case-only renames defeat orphan-cache adoption: case-sensitive path compare vs case-insensitive FAT exists()

`lib/Epub/Epub.cpp:617-620` — verifier votes 3/3

FAT LFN lookups are case-insensitive/case-preserving. If the user renames a book or any parent folder changing only letter case (e.g. "sharpe's battle" -> "Sharpe's Battle" or fixing an author folder's capitalization), the new path hashes to a different cache key, so load() takes the adoption path. The scan finds the orphan sidecar, but storedPath differs from filepath only by case: the case-SENSITIVE std::string compare at line 619 does not match, and then Storage.exists(storedPath) at line 620 — which is case-INSENSITIVE on FAT — returns true because it matches the book's own renamed file. The guard concludes 'original still present, don't steal' and skips adoption. Result: the exact scenario feature #5 was built for (a manual SD rename) silently loses reading progress whenever the rename is case-only, or when any path segment's case changed. The same class of mismatch exists in writeContentKeySidecar's skip check (line 566, 'p == filepath'), which merely causes a redundant rewrite.

**Fix:** Before the exists() guard, compare storedPath against filepath with an ASCII case-insensitive comparison (like the equalsIgnoreCase helper already in FileBrowserActivity.cpp:46-54): if they match ignoring case, treat the exists() hit as the book itself and adopt. Ideally compare per-path-segment case-insensitively so parent-folder case changes are also recognized.

#### F7. Prewarm walk has no macOS/hidden-file filtering — AppleDouble '._*.epub' files and dot-dirs are processed, creating permanent junk cache dirs and a meaningless failure count

`src/activities/settings/PrewarmCoversActivity.cpp:56-66` — verifier votes 3/3

stepWork's directory expansion pushes every subdirectory and every *.epub file with no metadata filtering. On this user's macOS/Dropbox-managed SD card, Finder copies create AppleDouble resource forks ('._12 Sharpe's Battle - Bernard Cornwell.epub') which end in .epub and pass FsHelpers::hasEpubExtension — potentially one per book — and hidden dirs (.trash etc.) are descended into. The file browser explicitly filters these (FileBrowserActivity.cpp:41-44 isMacOSMetadataEntry: name.rfind("._", 0) == 0, applied in acceptCommon at 94-99), so the user never sees them — but prewarm processes them. Per junk file: 'epub.setupCacheDir()' unconditionally creates a permanent, empty /.crosspoint/epub_<hash> dir even though load() fails (not a zip; no reaper exists — roadmap #8 unimplemented); failed++ makes the DONE screen report hundreds of scary failures for files that aren't books, hiding real broken books; each junk file wastes a zip-open attempt; and every junk dir further slows the O(N) adoption scan.

**Fix:** In the expansion loop, skip entries where name[0] == '.' (covers '._' AppleDouble forks and dot-dirs) and reuse the browser's isMacOSMetadataEntry/isWindowsMetadataEntry helpers — hoist them out of FileBrowserActivity's anonymous namespace into FsHelpers so both call sites share them. Combined with removing the pre-load setupCacheDir() call, failed loads then leave no orphan cache dirs.

#### F8. Prewarm's pendingFiles vector is unbounded — a large flat folder aborts (reboots) the device under -fno-exceptions

`src/activities/settings/PrewarmCoversActivity.cpp:57-68` — verifier votes 2/3

When expanding a directory, stepWork() pushes EVERY epub path in it into pendingFiles with no cap. The file browser caps in-RAM listings at INDEX_THRESHOLD=200 and switches to an on-SD index precisely because folders can be huge, but the prewarm walk has no such bound. Each stored path costs ~sizeof(std::string) 24 B + heap for the full path (e.g. '/books/Fiction/Bernard Cornwell/Sharpe/12 Sharpe's Battle - Bernard Cornwell.epub' ~= 84 chars -> ~120 B total per entry). A flat dump folder of 1,000 epubs ~= 120 KB plus reallocation transients (vector doubling holds old+new arrays simultaneously) on a device with ~150-250 KB free heap — and the very next step runs a full epub metadata build + JPEG decode. With -fno-exceptions, a failed vector reallocation calls abort(): the maintenance action crash-reboots instead of degrading. The header comment's claim 'one directory's file list ... RAM-safe' only holds for the current tidy folder layout.

**Fix:** Bound the per-directory batch: stop collecting at e.g. 200 files and remember the directory needs another pass (re-open and skip already-processed names, or keep the FsFile directory handle open across steps as a member and pull one entry per stepWork call). Reserve() with a cap and treat push_back beyond it as 'requeue directory'.

#### F9. Prewarm never issues a full/half e-ink refresh — up to ~230 consecutive FAST_REFRESH progress paints accumulate ghosting, and on cached re-runs it repaints near-continuously

`src/activities/settings/PrewarmCoversActivity.cpp:111-113,148` — verifier votes 3/3

The WORKING render calls 'renderer.displayBuffer(HalDisplay::RefreshMode::FAST_REFRESH)' and the WARNING/DONE renders call 'renderer.displayBuffer()' whose default is also FAST_REFRESH (GfxRenderer.h:168). Over 1,852 books that is ~231 consecutive partial refreshes with no periodic full/half refresh anywhere in the activity — the reader, by contrast, does a periodic full refresh every N pages (SETTINGS.getRefreshFrequency). Ghosting will build for the entire 30-90 min run and remain on the DONE screen. Additionally the repaint cadence is count-based (RENDER_EVERY=8 books), not time-based: on a re-run over an already-cached library each stepWork is only ~50-200 ms (cache-hit load + exists checks), so the panel is asked to FAST_REFRESH roughly every 0.5-1.5 s continuously for the whole walk — needless panel wear and battery drain for a progress counter.

**Fix:** Throttle progress paints by time (e.g. only requestUpdate when >=2-5 s elapsed since the last paint), do a HalDisplay::HALF_REFRESH every ~20-30 progress paints to clear ghosting, and render the DONE screen with a half/full refresh so the finished screen is clean.

#### F10. Jump-to-letter hold (#4) races the render task over the shared index-row cache and FileIndex handle — data race on std::string with crash potential in indexed folders

`src/activities/home/FileBrowserActivity.cpp:879-891` — verifier votes 3/3

Rendering runs on a separate FreeRTOS task (ActivityManager::begin creates 'ActivityManagerRender', ActivityManager.cpp:26-34) and Activity::loop() runs on the Arduino loop task WITHOUT the render lock (ActivityManager.cpp:67: 'do not hold a lock here'). The fork's continuous-hold callbacks call letterJumpIndex(), which in index mode (folders >200 entries) performs a linear scan calling entryNameAt() for up to every row (lines 233-243). entryNameAt() (lines 309-328) mutates shared state: it writes indexCachedNames[slot] (std::string::assign), indexCachedRows[slot], the single shared *indexEntry buffer, and seeks/reads the shared fileIndex FsFile handle. Meanwhile the render task, triggered by the PREVIOUS 500 ms hold tick (ButtonNavigator continuousIntervalMs=500 default), is concurrently inside render() calling entryNameAt() through the rowTitle/rowValue/rowIcon lambdas on the same arrays and file handle. Concurrent std::string assign vs c_str() read is a heap-corruption/use-after-free class race; concurrent seek/read on one FsFile garbles both readers. Upstream's continuous handlers were pure arithmetic (nextPageIndex), so this cross-task access pattern is fork-introduced. The scan also evicts the render task's warm cache slots every tick, forcing extra SD reads per repaint. Only manifests in Books-mode folders above INDEX_THRESHOLD=200, so it will be intermittent — the worst kind of on-device crash to debug.

**Fix:** Serialize the scan with rendering: wrap the jump in the existing lock pattern (already used at FileBrowserActivity.cpp:275-278): '{ RenderLock lock(*this); selectorIndex = letterJumpIndex(true); } requestUpdate();' in both continuous callbacks. Cheap, and bounds the race window to zero; the scan is short enough (<0.5 s worst case) that briefly blocking a repaint is fine.

#### F11. lastBrowsePath (#3) rewrites the whole state.json non-atomically on every folder navigation — SD latency per button press and a greatly enlarged power-loss corruption window for ALL app state

`src/activities/home/FileBrowserActivity.cpp:247-253` — verifier votes 3/3

loadFiles() runs on every navigation (descend, ascend, delete-refresh, hidden-files toggle, entering the browser from a reader), and the fork persists the path change immediately: APP_STATE.saveToFile() serializes the ENTIRE CrossPointState — openEpubPath, pending bookmark jump, sleep-image state (JsonSettingsIO.cpp:105-126) — and rewrites /.crosspoint/state.json in place via Storage.writeFile (open with O_WRONLY|O_CREAT|O_TRUNC, no temp+rename; JsonSettingsIO.cpp:125 'return Storage.writeFile(path, json);'), preceded by a mkdir probe (CrossPointState.cpp:40-43). Upstream saves state only at coarse checkpoints (book open/close, sleep, pin favorite — ~15 call sites, e.g. SleepActivity.cpp:384, EpubReaderActivity.cpp:1723); the fork multiplies write frequency 10-100x during browsing (a Genre/Author/Series descent is 3+ writes). Consequences on device: (1) a synchronous SD write (~10-100 ms) inserted between the button press and the folder listing on the hottest interactive path, plus continuous small FAT writes/wear; (2) a battery pull or crash mid-write truncates state.json, loadState() then fails JSON parse (JsonSettingsIO.cpp:130-134) and loadFromFile() falls back to state.bin — which was renamed to state.bin.bak after the original migration (CrossPointState.cpp:55-60) — so ALL state silently resets to defaults: the device forgets the currently-open book (boot resume), sleep image preferences, pending bookmark, and lastBrowsePath itself. The persisted value is only ever consumed when 'Browse Files' is chosen from Home (HomeActivity.cpp:1745-1752), so intermediate saves are pure wasted work; only the last folder before leaving the browser matters. The basepath != lastBrowsePath guard only dedupes same-folder refreshes, not navigation.

#### F12. content.key sidecar written non-atomically (truncate-in-place); a torn write defeats the anti-steal guard and lets a duplicate book steal a live cache

`lib/Epub/Epub.cpp:556-577` — verifier votes 2/3

writeContentKeySidecar() writes via Storage.writeFile(), which is open(O_WRONLY|O_CREAT|O_TRUNC)+write+close (HalStorage.h:27-29 'Overwrites existing file'; simulator impl HalStorage.cpp:422-428). Power loss / battery death mid-write leaves a truncated sidecar. The adoption parser handles a missing newline safely (skipped at line 614), but the dangerous case is 'key line complete, path line truncated': strtoull still yields the correct key, storedPath is a garbage prefix, so Storage.exists(storedPath) at line 620 is false and the 'original still present -> don't steal' guard is defeated. With duplicate copies of the same book (same title|author => same fnv key — common in real libraries), opening/renaming copy A can then rename away copy B's LIVE cache dir, destroying B's reading progress, stats and reader settings, which get silently rebuilt from scratch. On e-readers that die at 0% battery, torn writes of small files are a realistic event, and this sidecar is rewritten on load whenever the recorded path differs.

**Fix:** Write atomically: write to <cachePath>/content.key.tmp, close, Storage.remove(content.key), Storage.rename(tmp, content.key). In the adoption scan, additionally reject malformed sidecars instead of trusting them: require storedPath to start with '/' and end with a supported book extension before treating exists()==false as 'orphan'; skip adoption otherwise.

#### F15. Cancel and the power/sleep gesture are blocked for the full duration of each book's processing — contradicts the 'never blocks the UI' contract

`src/activities/settings/PrewarmCoversActivity.cpp:99-114` — verifier votes 3/3

#### F16. Prewarm walk truncates long UTF-8 filenames: 256-byte name buffer vs FAT LFN max ~765 UTF-8 bytes (browser uses 500, FileIndex 511)

`src/activities/settings/PrewarmCoversActivity.cpp:56-67` — verifier votes 2/3

FAT long filenames hold up to 255 UTF-16 units, which is up to ~765 bytes in UTF-8 (CJK/Cyrillic titles commonly exceed 256 bytes well before 255 characters). The prewarm walk reads names into char name[256] and never checks getName()'s return value (the buffer is also uninitialized if getName fails). A book file whose UTF-8 name exceeds 255 bytes gets a truncated 'child' path: hasEpubExtension() then fails (".epub" cut off) and the book is silently skipped from the count; a long-named directory yields a nonexistent path pushed to dirStack, so its entire subtree is silently skipped. The file browser handles the same names fine (NAME_BUFFER_SIZE=500, FileBrowserActivity.cpp:30; FileIndex::MAX_NAME=511), so the user sees books in the browser that prewarm never touches, with no error reported.

**Fix:** Use a 512-byte buffer (matching FileIndex::MAX_NAME+1), initialize name[0]='\0', and check getName()'s return value — on 0/failure, count the entry as failed++ (or log it) instead of silently building a truncated path.

#### F17. firstSortChar ignores non-ASCII letters: 'Émile Zola' groups under 'm', accented/non-Latin names get garbage letter groups

`lib/FsHelpers/NaturalSort.cpp:110-118` — verifier votes 2/3

firstSortChar walks bytes and only accepts isdigit/isalpha, both false for UTF-8 lead/continuation bytes (0x80-0xFF are not alpha in the C locale on newlib/ESP32). For 'Émile Zola - ...' (É = 0xC3 0x89) both bytes are skipped and the function returns 'm' — the first ASCII letter — so the entry belongs to the 'm' group; 'Éric-Emmanuel Schmitt' returns 'r'; a fully non-ASCII name (Cyrillic/CJK) returns 0. Since naturalCompare sorts multibyte names byte-wise after 'z', accented authors cluster at the list end where each name's arbitrary skipped-ahead letter differs from its neighbour's — the hold-to-jump gesture (letterJumpIndex, FileBrowserActivity.cpp:227-245) then degrades to stepping one entry at a time through that section, and jumping 'forward from Z' lands mid-alphabet letters again. The unit tests (test/natural_sort/NaturalSortTest.cpp) cover no multibyte input at all.

**Fix:** Decode the first UTF-8 codepoint instead of scanning bytes: if the lead byte is >= 0xC0, decode the codepoint and map Latin-1/Latin Extended-A accents to their base ASCII letter (É→e, Ö→o, Å→a — a ~64-entry table covers the common ranges); bucket anything else non-ASCII into a single dedicated group (e.g. return 0x7F) so such names form one stable group at the end rather than pseudo-random letters. Add multibyte cases to NaturalSortTest.

#### F18. letterJumpIndex: unbounded per-row SD scans in indexed (>200 entry) folders, and the hold gesture degenerates to jump-to-end in all-numbered/single-letter folders — losing the old page jump

`src/activities/home/FileBrowserActivity.cpp:227-245` — verifier votes 3/3

Two related defects in the Books-mode hold gesture that replaced page jumping (lines 879-891). (1) In index mode (folders above INDEX_THRESHOLD=200 — the mode this feature most targets), every entryNameAt(k) miss performs fileIndex->entryAt(row,...) — an offsets-block read plus seek + 2 reads of the record from the .idx file (FileIndex.cpp:651-682, ~0.5-2 ms each) — and a std::string assign into the 32-slot row cache. letterJumpIndex scans linearly row-by-row from the cursor (backward scans up to twice the group, lines 240-243), so one jump across a large letter group (hundreds of same-letter authors in a >200-entry genre folder of this 1,852-book library) issues hundreds to thousands of SD reads inside a single loop() call — a multi-second stall per repeat — and the gesture re-fires every 500 ms while held (ButtonNavigator continuousIntervalMs = 500), blocking input and hammering the SPI bus for the whole hold. The scan also flows straight through the 32-entry row cache (row % 32), evicting the rows visible on screen so the subsequent render re-reads them from SD. (2) firstSortChar collapses every digit-leading name to the single group '0' (NaturalSort.cpp:114 'if (isdigit(c)) return '0';'), so in this user's series folders — where every file is '01..24 Title - Author.epub', up to ~95 entries — the whole folder is one group: the forward scan finds no boundary and returns n-1, backward returns 0. The pre-existing hold behavior (nextPageIndex/previousPageIndex, still used in PickFirmware mode at lines 882/889) paged in screen-sized steps; in Books mode that mid-folder navigation is gone for numbered folders (and any all-one-letter single-author folder), leaving only first/last teleports — a usability regression for the fork's primary use case. Vector mode (<=200 entries) is RAM-only and fine.

**Fix:** Exploit sortedness instead of linear scanning: exponential galloping + binary search on firstSortChar (probe cur+1, cur+2, cur+4 ... then bisect) for O(log n) index reads per jump, reading names into a local FileIndex::Entry buffer that bypasses the render row cache; or cache a small first-letter→row table (36 entries) once per indexed folder open. When no group boundary exists (all-numbered/single-letter folder), fall back to ButtonNavigator::nextPageIndex/previousPageIndex with the already-computed pageItems so hold behaves like page jump inside a single group, instead of returning n-1/0. Alternatively cap the per-tick scan (~200 rows) and continue on the next 500 ms tick.

#### F20. Guide 'start' fallback (#2) silently no-ops when the start href carries a #fragment, and the miss is baked into book.bin

`lib/Epub/Epub.cpp:282-283` — verifier votes 2/3

The fork stores the guide start reference as bookMetadata.textReferenceHref, but ContentOpfParser keeps the raw href including any anchor fragment (built at ContentOpfParser.cpp:301 as normalisePath(decodeUriEscapes(baseContentPath + atts[i+1])) — '#' fragments are preserved), and Epub::getSpineIndexForTextReference matches it against spine hrefs with an exact string compare ('if (getSpineItem(i).href == bookMetadataCache->coreMetadata.textReferenceHref)', Epub.cpp:1349).
